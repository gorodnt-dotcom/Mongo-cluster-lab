# MapleGrove — Simple MongoDB Sharded Cluster

A minimal sharded MongoDB cluster for the assignment, built with Docker Compose.

## Topology

- **cfg1 / cfg2 / cfg3** — config server replica set (`cfgrs`), 3 nodes, ports 27019 / 27021 / 27022
- **shard1a / shard1b** — shard replica set (`shard1rs`), 2 nodes, ports 27018 / 27023
- **shard2a / shard2b** — shard replica set (`shard2rs`), 2 nodes, ports 27020 / 27024
- **mongos** — query router, port 27017 (this is what clients connect to)
- **setup** — one-shot container that initiates the replica sets and registers the shards, then exits

Notes:
- A 2-member replica set has no tiebreaker, so a write concern of `majority` needs both nodes up, and losing one member stalls automatic failover until it comes back (or you add an arbiter). That's fine for this lab's purposes.
- Each `mongod` is capped with `--wiredTigerCacheSizeGB` (0.25GB for config servers, 0.5GB for shard members). Without a cap, every node defaults to ~50% of the *host's* visible RAM, and 7 mongod processes doing that simultaneously will over-subscribe memory and get OOM-killed under load — that's exactly what happened during testing before the cap was added.

## Usage

Start the cluster (also runs setup automatically):

```bash
docker compose up -d
```

Watch the setup logs until it finishes:

```bash
docker compose logs -f setup
```

Connect through the router:

```bash
docker compose exec mongos mongosh --port 27017
```

Check shard status from inside mongosh:

```js
sh.status()
```

The `setup` container only creates the replica sets, adds the shards, and enables sharding on the `maplegrove` database — it doesn't load any data. That's done by the workload generator below.

Tear down:

```bash
docker compose down        # keep data
docker compose down -v     # also wipe data volumes
```

## Document model

The workload models e-commerce **product view events** — one document per (customer, product, moment) view. Collection: `productViews` (loaded twice, into two collections, for the shard key comparison below).

```js
{
  _id: ObjectId,
  customerId: 25000,             // int, 0..49999 (50,000 distinct customers)
  productId: "SKU-00913",        // string, "SKU-00001".."SKU-05000" (5,000 distinct SKUs)
  viewTimestamp: ISODate("..."), // uniformly distributed over a trailing 30-day window
  sessionId: "b1e2...uuid4",     // one per event; no session-level grouping modeled
  referrer: "search",            // "search" | "recommendation" | "direct" | "email" | "social"
  deviceType: "mobile"           // "mobile" | "desktop" | "tablet"
}
```

Flat and denormalized on purpose: for a view-event stream you almost always write once and read by `productId` or `customerId`, so there's no reference to join back to a `products` or `customers` collection — this event *is* the analytics record.

## Synthetic workload

Generated by `scripts/workload_and_shard_key_comparison.py`:

- **500,000 view events**
- **50,000 customers** — `customerId` drawn uniformly at random per event
- **5,000 SKUs**, of which **5% (250 SKUs) are "hot"** and jointly receive **60% of all views** (300,000 of the 500,000); the remaining 4,750 "cold" SKUs share the other 40%. Within each tier, views are uniform — this is a deliberately simple two-tier approximation of a Zipf-like popularity curve, not a full Zipf distribution, matching the assignment's stated 5%/60% split exactly.
- The 250 hot SKUs are a **random sample** across the full id space (not the first 250 ids) — real product popularity has nothing to do with when an id happened to be assigned, and clustering the hot ids together would have made the compound shard key look artificially better than it would in practice.
- `viewTimestamp` uniformly distributed over a trailing 30-day window.

Run it against a live cluster:

```bash
python -m venv .venv && source .venv/bin/activate   # if not already set up
pip install -r scripts/requirements.txt
python scripts/workload_and_shard_key_comparison.py
```

It generates the 500,000 events once, then loads the **identical dataset** into two sharded collections so the only variable is the shard key:

- `maplegrove.productViews_hashed` — shard key `{ productId: "hashed" }`
- `maplegrove.productViews_compound` — shard key `{ productId: 1, viewTimestamp: 1 }`

For the compound collection, it also pre-splits at the SKU id midpoint and moves the upper half to `shard2rs` — an ascending range key starts as a single unsplit chunk on one shard, and letting the balancer alone catch up would take a while to kick in at this small (~100MB) data size (default chunk size is 128MB). This mirrors the manual split/move technique noted above for the topology demo.

## Shard key comparison & access patterns

Full test results (measured shard distribution, `explain()` output for the 4 required access patterns, and the analysis) are in **[shard-key-comparison.md](shard-key-comparison.md)**.

Short version: hashed `productId` and compound `{ productId, viewTimestamp }` both land the workload roughly 50/50 across the two shards, but for equality-on-`productId` queries (the assignment's primary access patterns) the compound key gets its supporting index for free from the shard key, while the hashed key needs a separate secondary index to match it. For queries that don't filter on `productId` (a time-only dashboard query, a customer lookup), neither key helps — both scatter-gather across every shard regardless.

## Notes

- `mongos` is the single entry point for applications; it routes reads/writes to the correct shard.
- The config server stores cluster metadata (which shard owns which chunks).
- If you restart the stack from scratch after `down -v`, the `setup` container will re-initiate everything cleanly.
- Re-running `workload_and_shard_key_comparison.py` is safe — it drops and recreates both comparison collections each time.
